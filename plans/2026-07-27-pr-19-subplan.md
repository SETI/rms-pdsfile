## 1. What moves

Eight definitions, located **by symbol**. The parent plan's ":4642–4896" and
":4358–4640" windows are against the 6,304-line original; PR-15 through PR-18
have all edited this file and it is 5,125 lines at the parent tip. On that tip
the targets are exactly two consecutive banner blocks, `pdsfile.py:3779–4318`:

| Banner | Lines | Definitions |
|---|---|---|
| `# Support for PdsFile objects representing index rows` | 3779–4061 | `get_indexshelf`, `find_selected_row_key`, `child_of_index`, `data_abspath_associated_with_index_row`, `data_pdsfile_for_index_row` |
| `# OPUS support methods` | 4063–4317 | `from_filespec` (classmethod), `from_opus_id` (classmethod), `opus_products` |

They become **`class _IndexRowsMixin`** in **`src/pdsfile/_index_rows.py`** and
**`class _OpusMixin`** in **`src/pdsfile/_opus.py`**.

**Neither block contains a class-level assignment**, so the "class attributes
stay on `PdsFile`" rule has nothing to catch here — verified by an AST pass over
both windows, which finds eight `FunctionDef`s and no `Assign`. That is
different from PR-17 (six shelf attributes) and PR-18 (`LOG_ROOT_`), and the
verification is recorded whichever way it comes out.

### 1.1 `from_filespec` is in `_opus.py`, and that is not an accident

`from_filespec` is an alternative constructor, so a reader will ask why it is not
with the other `from_*` constructors. Two independent authorities put it here:
the parent plan's PR-19 window (":4642–4896") contains it, and the file's own
`# OPUS support methods` banner contains it. **The banner boundary is the
boundary** for this PR, in both directions.

### 1.2 The index-related *properties* do not move

`indexshelf_abspath`, `is_index`, `index_pdslabel` and `filename_keylen` are
lazy properties in the `# Properties` banner block (`pdsfile.py:1084–2642`).
They belong to **PR-22**'s `_PropertiesMixin`. The moved methods read them
through `self.`, which is an MRO lookup at run time, so the two halves may live
in different modules.

## 2. Move order — two modules, two commits, and which one goes first

`_index_rows.py` is created **first**, `_opus.py` second, each as its own pure-move
commit with the tree green in between. The reasons, in order:

1. **`_index_rows.py` is the mechanically simpler of the two.** Its sweep names
   three module-level imports and **no class**; `_opus.py`'s names a class —
   `PdsFile` itself — and is the one place in all of Phase 5 that needs a
   function-local deferred import (§4.2). Landing the simple move first means
   that if a gate goes red at the second commit, the deferred import is the only
   new thing it can be about.
2. **The two blocks are adjacent and independent.** Neither block's code calls
   the other's names: a cross-reference check over both windows finds no call
   from an index-row method to an OPUS method or the reverse. So either order
   leaves an importable tree, and the choice is free to be made on
   reviewability.
3. **Alphabetical base order gives the same sequence anyway.**
   `_IndexRowsMixin` sorts before `_OpusMixin`, so commit 1 inserts a base ahead
   of the slot commit 2 uses, and neither commit has to re-sort what the other
   wrote.

The tree is importable and every gate is green at **both** commits, not just at
the second; that is checked, not assumed.

## 3. The sweep, done mechanically — and in both directions

**Direction 1 — what must move with the code.** The PR-16/PR-17/PR-18 two-pass
method: CPython's `symtable` for the module-global names each moved definition's
*body* references, plus an AST pass over each definition's *decorator expressions
and argument defaults*, which are evaluated in module scope and which `symtable`
does not attribute to the method. The second pass is not optional — it is what
caught PR-16's `_GLOB_CACHE_SIZE` and PR-17's `PATH_EXISTS_CACHE_SIZE`, both
referenced only inside an `@functools.lru_cache(maxsize=…)` argument. The full
output, **including its "nothing else" lines**, goes in the validation record.

Run on the parent tip, it says:

| Module | body references | decorator/default references |
|---|---|---|
| `_index_rows.py` | `_clean_join`, `numbers`, `pdstable` | none |
| `_opus.py` | `_needs_glob`, `abspath_for_logical_path`, `defaultdict`, **`PdsFile`** | none |

so `_index_rows.py` gets `import numbers`, `import pdstable` and
`from ._path_utils import _clean_join`; `_opus.py` gets
`from collections import defaultdict` and
`from ._path_utils import _needs_glob, abspath_for_logical_path`, plus §4.2's
deferred import for `PdsFile`. Neither `_path_utils` nor `collections` imports
`pdsfile.pdsfile`, so neither import is a cycle; that is checked rather than
assumed.

**Direction 2 — who *patches* what this PR moves** (deferred entry 29, owned by
"PR-17 onward"). The free-variable sweep cannot see a test that patches a name on
a module the code no longer resolves through; such a test keeps passing while
testing nothing, and §6.2's outcome-set diff is *structurally blind* to it.
Steps, unchanged from PR-17 §2 and PR-18 §2:

1. grep all of `tests/` and `scripts/` for `monkeypatch.setattr`/`setitem`/
   `delattr`/`setenv`/`delenv`, `mock.patch`, `patch(`, `patch.object`,
   `setattr(`, and direct module- or class-attribute assignment;
2. enumerate every site whose target names `pdsfile.pdsfile` or any of the eight
   symbols this PR moves, and classify each as still-reaching or broken;
3. for every such site, **prove the test still goes red when the patched
   behavior is wrong** — force the patched call to answer wrongly and confirm
   the failure;
4. this PR's own extra: `get_indexshelf` and `find_selected_row_key` reach the
   shelf layer, and `opus_products` walks the rule subclasses and the
   filesystem, so the patch targets to look hardest at are `_get_shelf`,
   `glob_glob`, `os_path_exists` and the class registries.

**Every negative control asserts which file it imported.** `pyproject.toml` sets
`pythonpath = [".", "src"]`, which pytest resolves against **rootdir** and
inserts **ahead of `PYTHONPATH`**, so mutating a copy of `src/` and pointing
`PYTHONPATH` at it from the repo root imports the *unmutated* tree and every
control comes back green — which reads exactly like "no test covers this". PR-18
fell into this and re-ran all seven of its controls
(`critiques/phase5-validation.md`, PR-18 §9). Each mutation is therefore written
into a **full copy of the working tree**, pytest is run **from inside that
copy**, and a `conftest.py` there prints the mutated module's `__file__` so the
run asserts what it imported.

## 4. Two pinned decisions the parent plan makes — neither is re-litigated

### 4.1 The `cls.__bases__[0].__name__ == 'Pds4File'` sniff moves byte-for-byte

It sits in `data_abspath_associated_with_index_row`'s nested `get_keys`. The
parent plan is explicit that it is **not** broken by this refactor and that
replacing it — with `issubclass`, an inherited class flag, or anything else —
would not be behavior-identical, so it moves **unchanged**. This sub-plan adds
one obligation the plan does not: **verify the claim rather than repeat it.**
`cls` there is `type(self)`, a *rule* subclass, and the claim is that a rule
subclass's `__bases__[0]` is unaffected by adding mixin bases to `PdsFile`. So
dump, for all 34 classes in the hierarchy, `__bases__[0].__name__`, the full
`__bases__` tuple and the full MRO, on the parent tip and at HEAD, and diff: the
only permitted difference is `PdsFile`'s own `__bases__`/MRO gaining the two new
mixins.

Then record the string-sniff fragility in
`critiques/deferred-observations.md` as a **phase-"b"** item. Checked first: it
is not among entries 1–48 today.

### 4.2 Cross-module references resolve the way the code does today

- **Names** are resolved by `__name__`, as the sniff above does. Nothing is
  changed to import `Pds4File` into a base module — that is a cycle.
- **The one class object.** `opus_products` contains
  `direct_pds_subclasses = PdsFile.__subclasses__()`, which the Phase-5 preamble
  names as the only bare class-object reference in the whole phase. In `_opus.py`
  it becomes a **function-local deferred import** in `opus_products`' body:

  ```python
  from pdsfile.pdsfile import PdsFile
  ```

  **Module level would be a cycle** — `pdsfile.py` imports `_opus` to build the
  class — so the placement is checked mechanically (parse the module; assert no
  module-level `from pdsfile.pdsfile import` of any spelling), not by eye.
- **The preamble's "only one" claim is confirmed, not assumed.** Sweep both new
  modules for any *other* bare `PdsFile` / `Pds3File` / `Pds4File` reference and
  record what the sweep found, including "nothing else".

## 5. Deferred entry 48 — widening the mixin shadowing check

Entry 48 (raised by PR-18's round 4, **owner: PR-19**):
`tests/api/test_mixin_collisions.py::test_no_mixin_is_shadowed_by_pdsfile_itself`
intersects each mixin's names with `PdsFile`'s own and stops there, but the
subclasses are where the method surface is actually extended and are what the
tools and OPUS instantiate. PR-18 measured the intersection empty for both
subclasses against all three mixins, so nothing is broken; the check is simply
narrower than its name.

It lands here because **this PR is exactly the case the entry is about**:
`_OpusMixin` carries `opus_products` and `from_opus_id`, and OPUS support is
where the rule subclasses override most. It is inside this PR's deliverables
rather than a volunteered Deferred item (common brief §5.1).

**Shape:** a *new* test function alongside the existing one, not a
re-parametrization of it — so no existing test id changes and the set diff shows
additions only. It intersects each mixin's defined names with each subclass's,
for the subclasses reached from `PdsFile.__subclasses__()` (which is exactly
`Pds3File` and `Pds4File`, both imported explicitly so the check cannot pass
vacuously by discovering nothing).

**The intersection is re-measured with the two new mixins included, before the
test is written. A non-empty intersection is a hard stop to the coordinator** —
it would mean the extraction changed name resolution — not something to resolve
here.

Every id this adds is enumerated in the PR and in the validation record, in both
the `--mode ns` count and the no-holdings count (`tests/api/conftest.py` marks
the directory `holdings_free`).

## 6. Keeping `pdsfile.pdsfile.X` resolving

The measured invariant is `sorted(vars(pdsfile.pdsfile))`: **no name lost**.

Unlike PR-18, this PR **does** strand module-level names. After the move,
`numbers`, `pdstable` and `defaultdict` have **no remaining reference** in
`pdsfile.py` — measured, not guessed — and all three are **frozen manifest
members** of `pdsfile.pdsfile` (`tests/api/api_manifest.json`: `numbers` and
`pdstable` `"kind": "module"`, `defaultdict` `"kind": "class"`). So the imports
**stay**, in the PEP-484 redundant-alias form the file's header already uses for
six modules:

```python
import numbers as numbers
import pdstable as pdstable
from collections import defaultdict as defaultdict
```

An inline `noqa` and a ratchet grow are both forbidden (common brief §6.4), and
deleting them is a manifest break. `_clean_join`, `_needs_glob` and
`abspath_for_logical_path` keep live callers in `pdsfile.py` and so keep their
plain import form; that is measured per name.

Two names are **added** to `pdsfile.py`'s namespace, `_IndexRowsMixin` and
`_OpusMixin`, which the `class PdsFile` statement needs. Both are underscore
names, so the manifest does not see them.

## 8. Ruff ratchet

`per-file-ignores` may only shrink. Same per-code procedure PR-16, PR-17 and
PR-18 recorded, with the two traps their records name (`--isolated` drops
`pyproject.toml`'s `line-length = 100`, and ruff 0.15's default output format no
longer starts a line with the file path):

```
ruff check --no-cache --isolated --output-format concise --select <code> \
           --line-length 100 --target-version py310 <file>
```

1. For every code in `pdsfile.py`'s entry, run the above against the parent's
   `pdsfile.py`, this branch's `pdsfile.py`, `_index_rows.py` and `_opus.py`.
   **Each code must conserve**: parent count = the three post-move counts summed.
2. Each new module gets an entry listing **exactly** the codes its moved lines
   trigger, with the same explanatory comment the other moved-module entries
   carry. Every such code must already be in `pdsfile.py`'s entry — the entries
   are a **split**, not a new suppression. **A code that is not already there is
   a §6.4 hard stop.**
3. Any code `pdsfile.py` no longer triggers is **removed** from its entry.
4. The **converse** check, which is easy to skip: run the project's whole select
   set against each new module with **no** per-file entry, and confirm the
   violations reported are exactly the entry.

Moved bodies are **not** restyled to shed an inherited violation — that is a
content edit inside a move, and it belongs to PR-23.

## 10. Hard stops for this PR

ids §5 adds; a **non-empty** mixin/subclass name intersection (§5); a ruff code
needed by either new module that is not already in `pdsfile.py`'s entry; a moved

site that cannot be made to fail on wrong behavior; any temptation to "tidy"
anything inside `opus_products`, which is the largest and most heavily
golden-tested method in the file.
