## 3. The import graph, drawn before it is written

`preload_and_cache` is imported by `pdsfile.py` today, so making it a shim over
`_preload` while `pdsfile.py` also imports `_preload` is a three-way graph. Drawn:

```
   stdlib:  os   time   (pylibmc, optional)
                 │
                 ▼
        pdsfile/_path_utils.py          (imports only fnmatch, functools, glob, math, os)
                 │
                 ▼
        pdsfile/_preload.py  ◄────  from pdsfile import pdscache, pdsviewable
             ▲        ▲
             │        └────────  pdsfile/preload_and_cache.py   (9 re-export lines)
             │                            ▲            ▲
             │                            │            │
        pdsfile/pdsfile.py            pds3file/    pds4file/
             ▲                        __init__.py  __init__.py
             └────────────────────────────┴────────────┘
                        (from pdsfile.pdsfile import PdsFile)
```

Every edge points one way. **`_preload.py` never imports `pdsfile.pdsfile`**, at
module level or anywhere else, which is the Phase-5 preamble's pinned rule; §5
shows no moved body needs the class object, so it does not even need a
function-local deferred import.

`pdsfile.py` **stops** importing `preload_and_cache` (it imports `_preload`
instead); the shim stays live because `pds3file` and `pds4file` still import it,
which means the shim is exercised at package-import time by two modules rather
than only by an external caller.

**The one edge worth staring at** is `_preload.py`'s `from pdsfile import pdscache,
pdsviewable` — an import of the *package* from inside the package, while the
package's own `__init__.py` is mid-execution. It is the same form `pdsfile.py:34`
and `pds3file/__init__.py:9` already use, and `from <package> import <submodule>`
falls back to importing the submodule when the attribute is not yet bound, which is
exactly the partially-initialized case. Reasoning is not evidence, so §10 check 14
**executes four import orders in four fresh interpreters** — `import
pdsfile.pdsfile`, `import pdsfile.preload_and_cache`, `import pdsfile`, and
`import pdsfile._preload` — each printing the resolved `__file__` of every module
in the graph.

## 4. `preload_and_cache.py` becomes a re-export shim

**Measured before, so after can be diffed against it rather than argued about.**
`vars(pdsfile.preload_and_cache)` on the parent tip holds nine non-underscore
names, and they are exactly the manifest's record for that module:

```
DEFAULT_FILE_CACHE_LIFETIME  DICTIONARY_CACHE_LIMIT  FOEVER_FILE_CACHE_LIFETIME
LONG_FILE_CACHE_LIFETIME     SHORT_FILE_CACHE_LIFETIME
cache_lifetime_for_class     is_preloading   pause_caching   resume_caching
```

The shim re-exports all nine in the **PEP-484 redundant-alias form**, so they do
not read as unused imports and need neither a `noqa` nor a ratchet entry:

```python
from ._preload import DEFAULT_FILE_CACHE_LIFETIME as DEFAULT_FILE_CACHE_LIFETIME
...
from ._preload import resume_caching as resume_caching
```

**One line per name, not one parenthesized tuple.** Measured: ruff's isort runs
with `combine-as-imports = false` (the default), so the tuple form reports `I001`
and the split form is clean. `preload_and_cache.py` has **no** per-file-ignores
entry today and **must not gain one** (§7), so the shim is written in the form
that needs none. That is a choice about new code in a shim, not a restyle of a
moved body.

**Which import path `pdsfile.py` uses, and why.** `_preload` is now canonical, so
`pdsfile.py` imports from `._preload` rather than from the shim. Three reasons:
the shim is compatibility surface for *external* callers and pointing internal
code at it would make the shim load-bearing rather than compatibility; a direct
import keeps the graph in §3 acyclic by construction; and it keeps `pdsfile.py`'s
own header honest about where the code lives. `pds3file`/`pds4file` are **left
alone** — their `from pdsfile.preload_and_cache import cache_lifetime_for_class`
keeps working through the shim and keeps the shim exercised in-tree.

### 5.3 `pylibmc` — the one name this PR does not carry, and the measurement that settles it

`preload`'s `except pylibmc.Error` and the `HAS_PYLIBMC` flag come from one
try/except block at `pdsfile.py:38–42` whose only purpose is `preload`. It is a
module constant used by exactly one consumer, so it moves with its consumer —
the rule the common brief §2 states and PR-16 (`FILE_BYTE_UNITS`) and PR-17
(`PATH_EXISTS_CACHE_SIZE`) already applied. `HAS_PYLIBMC` is then re-exported.
`pylibmc` itself is a *conditionally bound module import*, and re-exporting it
would need a new `if HAS_PYLIBMC:` statement in `pdsfile.py` — new logic, not a
move.

Measured rather than reasoned: `pylibmc` **is not installed in this environment**,
so `pdsfile.pdsfile.pylibmc` does not exist here and §10 check 6's
`sorted(vars(pdsfile.pdsfile))` comparison cannot see it either way. To find out
what happens where it *is* installed, a stub `pylibmc.py` was put on `PYTHONPATH`
and `scripts/dump_public_api.py` was run: `pdsfile.pdsfile` then gains
`"pylibmc": "module"`, and diffing that dump against the committed manifest
reports **two extra names, both spelled `pylibmc` — one under `pdsfile.pdsfile`
and one under `pdsfile.pdscache`**, which has its own optional import of the same
module and which Phase 5 does not touch. So on any machine where the name exists,
the API-freeze gate is **already red today** and stays red after this PR for the
`pdscache` half; the name is not part of the frozen contract on either side. After
this PR the `pdsfile.pdsfile` occurrence resolves as `pdsfile._preload.pylibmc`.
Recorded in the validation record and carried to `critiques/deferred-observations.md`
rather than fixed here.

## 6. Commit sequence — three commits, and why in this order

`_preload.py` is built **bottom-up**: the machinery the mixin calls lands first,
the mixin second. The alternative — mixin first — would force commit 1 to write
`from .preload_and_cache import cache_lifetime_for_class, pause_caching,
resume_caching` into `_preload.py` and commit 2 to delete it again, leaving a
transient state that says the opposite of the final design.

| # | Title | Contents |
|---|---|---|
| 1 | `refactor: move the cache configuration and helpers into _preload.py` | new `_preload.py` = header + §1.4's 77 moved lines, byte-identical; `preload_and_cache.py` reduced to its nine re-export lines and a header that says what it now is; `pdsfile.py:44–46` retargeted from `.preload_and_cache` to `._preload` |
| 2 | `refactor: extract preload management into a mixin` | the 419 lines of §1.1 move into `_PreloadMixin`; `_preload.py` gains the imports the move requires (`os`, `time`, `pdscache`/`pdsviewable`, the `pylibmc` try/except, `_clean_abspath`/`_clean_join`); `pdsfile.py` gains `from ._preload import _PreloadMixin`, puts `_PreloadMixin` in its alphabetical base slot, and converts the five stranded names of §5.2 to their re-export form; `pyproject.toml` gains `_preload.py`'s ratchet entry |
| 3 | `style: give the remaining direct constructors their own banner` | three comment lines and a blank in `pdsfile.py` |

Commit 3 exists for the same reason PR-20's `48b0605` did: taking the
`# Preload management` banner with its block leaves `new_merged_dir`,

and every active gate green" §2's PR-discipline paragraph allows, and it is what
PR-17 through PR-20 each did. **The tree is importable and every gate is green at
all three commits**, not only at the last; that is checked, not assumed.

## 7. Ruff ratchet

`per-file-ignores` may only shrink. Same per-code procedure PR-16 through PR-20
recorded, with the two traps their records name (`--isolated` drops
`pyproject.toml`'s `line-length = 100`, and ruff 0.15's default output format no
longer starts a line with the file path):

```
ruff check --no-cache --isolated --output-format concise --select <code> \
           --line-length 100 --target-version py310 <file>
```

1. For every one of the 18 codes in `pdsfile.py`'s entry, run the above against
   the parent's `pdsfile.py`, this branch's `pdsfile.py` and `_preload.py`.
   **Each code must conserve**: parent count = the two post-move counts summed.
2. `_preload.py` gets an entry listing **exactly** the codes its moved lines
   trigger, with the same explanatory comment the other moved-module entries
   carry. Every such code must already be in `pdsfile.py`'s entry — the entries
   are a **split**, not a new suppression. **A code that is not already there is a
   §6.4 hard stop.**
3. Any code `pdsfile.py` no longer triggers is **removed** from its entry.
4. The **converse** check: run the project's whole select set against `_preload.py`
   with **no** per-file entry and confirm the violations reported are exactly the
   entry.
5. **`preload_and_cache.py` has no entry today and may not gain one.** If the shim
   would need a code, the shim is restructured — it is nine lines of new code, so
   there is always a form that needs none.

Measured on a prototype assembled from the real segments, before this plan was
finished: `_preload.py` triggers **E501, E701, F841, RUF005, UP015, UP031** — six
codes, all six already in `pdsfile.py`'s 18-code entry — and the shim in its
split-line form triggers **nothing**. Both figures are re-measured on the delivered
files.

Moved bodies are **not** restyled to shed an inherited violation; that is PR-23's
job.

## 11. What the green set will not prove — say it in the PR

`else` branch at `:711` needs `HAS_PYLIBMC` true *and* a non-zero port; neither

## 12. Hard stops for this PR

Any manifest diff at all; **any** pass/fail set movement, in either direction, in
either mode — this PR is licensed to add no test id; any name that resolves as
`pdsfile.preload_and_cache.X` or `pdsfile.pdsfile.X` today and does not afterwards
(other than `pylibmc`, §5.3, which is measured and recorded); a non-empty
mixin/subclass name intersection (§9); a ruff code needed by `_preload.py` that is
not already in `pdsfile.py`'s entry, or any code at all needed by the shim; a
moved body that cannot be kept byte-identical at its move commit; an import cycle
in any of the four orders of §3; a monkeypatch site that cannot be made to fail on
wrong behavior; and any temptation to "improve" anything inside `preload`, which
is the single most consequential method in the package and the one whose most
important branches nothing here can test.

## 13. As executed — where the work diverged from §1–§12

Appended after the fact rather than editing the sections above, so the plan that
was written first stays readable as what it was. Four statements above did not
survive contact with the code.

1. **§7 step 1's acceptance rule was not met by one code, and the exception is a
   shrink rather than a leak.** The rule reads "**Each code must conserve**:
   parent count = the two post-move counts summed." Seventeen of the eighteen do.
   **`I001` does not: 2 → 1 + 0.** The parent's `pdsfile.py` had two unsorted
   import blocks, at `:6` and at `:44`; removing the `pylibmc` try/except from
   between them merged the two into one, and `_preload.py`'s own header was

   contributes none. A ratchet that only shrinks is exactly what §7's first
   sentence requires, so the outcome is compliant — but the criterion as stated
   was "conserve", and this is where that belongs.

2. **§7 step 3 anticipated a code leaving `pdsfile.py`'s entry, and one did.**
   `UP015`'s only occurrence in `pdsfile.py` was
   `open(table_path, 'r', encoding='utf-8')` inside `load_volume_info`, so
   `pdsfile.py`'s entry drops it and `_preload.py`'s carries it. That is the step
   working as written; it is recorded because §7 says "which codes leave is
   recorded either way".

3. **Commit 3's title and its banner text are not §6's.** §6 planned
