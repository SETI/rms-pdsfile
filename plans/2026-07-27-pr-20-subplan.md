## 2. Three blocks, two modules — the mapping and why it is not three

The parent plan names exactly **two** module files for this PR, and the
coordinator settled the mapping before work started. It is recorded here, not
re-litigated:

| New module | Mixin class | Gets |
|---|---|---|
| `src/pdsfile/_associations.py` | `_AssociationsMixin` | the **associations** block only |
| `src/pdsfile/_sorting.py` | `_SortingMixin` | **split/sort *and* transformations** |

Two reasons, both stated in the PR body and the second one in `_sorting.py`'s
module docstring:

1. A third module (`_transformations.py`) would deviate from the stated
   deliverable, and a deviation needs an owner-acknowledged addendum (§6.4).
2. Split/sort and transformations are one domain — bulk operations over lists of
   basenames, logical paths, abspaths and `PdsFile` objects, with no I/O of their
   own. Associations are the category-crossing lookup layer that walks the
   holdings tree. The measured call graph agrees: **the associations call the
   transformations three times and the transformations never call back** (§4).

Because the filename `_sorting.py` undersells a module that also holds twelve
conversion helpers, its docstring says what it actually holds: *splitting,
sorting, and bulk conversion between PdsFile objects, abspaths, logical paths and
basenames*.

## 3. `is_logical_path` and the module-level tail stay in core

The parent plan is explicit:

> Note `is_logical_path` (classmethod at :6281) falls inside the associations
> line window but is a generic path predicate, not an association. It is a
> **public `PdsFile` classmethod** (frozen as `PdsFile.is_logical_path`), so it
> cannot become a plain module function without vanishing from the class
> surface — **leave it in core**. The associations proper end at
> `associated_parallel`.

So the associations window ends at `associated_parallel`'s last line (`:4567` on
the parent tip) and **not** at the end of the `# Associations` banner block.
`is_logical_path` (`:4569–4578`) and the module-level tail below the class —
`PdsFile.SUBCLASSES['default'] = PdsFile` and `PdsFile.cache_category_merged_dirs()`
— stay exactly where they are.

**This is the one window boundary in the PR that does not match a banner
boundary**, which is exactly what a mechanical block-move gets wrong, so it is
called out in the PR body, and §9's byte-for-byte check is run over the moved
set *and* over the not-moved remainder: `is_logical_path` must still be a member
of `PdsFile`'s own body at HEAD, byte-identical, and `PdsFile.is_logical_path`
must still resolve to `PdsFile` rather than to a mixin.

(Nothing in the plan says `is_logical_path` may not become a mixin method later.
It says leave it in core, and PR-22's stay-list names it again. It is left.)

## 4. The sweep, done mechanically — and in both directions

**Direction 1 — what must move with the code.** The PR-16/17/18/19 two-pass
method: CPython's `symtable` for the module-global names each moved definition's
*body* references (a name bound in an enclosing function scope is FREE, not
GLOBAL, so `is_global()` is exactly the module-global question), plus an AST pass
over each definition's *decorator expressions and argument defaults*, which are
evaluated in module scope and which `symtable` does not attribute to the method.
The second pass is not optional — it is what caught PR-16's `_GLOB_CACHE_SIZE`
and PR-17's `PATH_EXISTS_CACHE_SIZE`, both referenced only inside an
`@functools.lru_cache(maxsize=…)` argument. The full output, **including its
"nothing else" lines**, goes into the validation record.

Run on the parent tip, it says:

| Module | body references | decorator/default references |
|---|---|---|
| `_sorting.py` | `os`, `_clean_join`, `abspath_for_logical_path`, `logical_path_from_abspath` | **none** |
| `_associations.py` | `os`, `_clean_join`, `_needs_glob` | **none** |

**No module-level constant and no class object appears in either list.** In
particular neither module needs `PdsFile`, `Pds3File` or `Pds4File`, so — unlike
PR-19's `_opus.py` — **neither module needs a function-local deferred import**,
and both move commits can be pure. That is a measurement, and the sweep is
re-run at HEAD to confirm the delivered modules need nothing more.

So `_sorting.py` gets `import os` and
`from ._path_utils import _clean_join, abspath_for_logical_path, logical_path_from_abspath`;
`_associations.py` gets `import os` and
`from ._path_utils import _clean_join, _needs_glob`. `_path_utils` does not
import `pdsfile.pdsfile`, so neither import is a cycle; that is checked rather
than assumed.

**Direction 2 — who *patches* what this PR moves** (deferred entry 29, owned by
"PR-17 onward"). The free-variable sweep cannot see a test that patches a name on
a module the code no longer resolves through; such a test keeps passing while
testing nothing, and §6.2's outcome-set diff is *structurally blind* to it.
Steps, unchanged from PR-17 §2, PR-18 §2 and PR-19 §3:

1. grep all of `tests/` and `scripts/` for `monkeypatch.setattr`/`setitem`/
   `delattr`/`setenv`/`delenv`, `mock.patch`, `patch(`, `patch.object`,
   `setattr(`, and direct module- or class-attribute assignment;
2. enumerate every site whose target names `pdsfile.pdsfile` or any of the 27
   symbols this PR moves, and classify each as still-reaching or broken;
3. for every such site, **prove the test still goes red when the patched
   behavior is wrong** — force the patched call to answer wrongly and confirm
   the failure;
4. this PR's own extra: **the sort layer is where a test pins
   directory-enumeration order**, and `associated_parallel` reaches the rules,
   the shelf layer and the filesystem layer, so the patch targets to look hardest
   at are `glob_glob`, `os_path_exists`, `os_listdir`, `_get_shelf`,
   `shelf_path_and_key_for_abspath` and the `CACHE` / `LOCAL_PRELOADED` class
   registries.

**Every negative control asserts which file it imported.** `pyproject.toml` sets
`pythonpath = [".", "src"]`, which pytest resolves against **rootdir** and
inserts **ahead of `PYTHONPATH`**, so mutating a copy of `src/` and pointing
`PYTHONPATH` at it from the repo root imports the *unmutated* tree and every
control comes back green — which reads exactly like "no test covers this". PR-18
fell into this and re-ran all seven of its controls
(`critiques/phase5-validation.md`, PR-18 §9). Each mutation is therefore written
into a **full copy of the working tree**, pytest is run **from inside that
copy**, and a `conftest.py` there prints the mutated modules' `__file__` so the
run asserts what it imported.

## 6. Move order — two modules, two commits, and which one goes first

`_sorting.py` is created **first**, `_associations.py` second, each as its own
pure-move commit with the tree green in between. The reasons, in order:

1. **`_associations.py` carries the boundary that is not a banner boundary**
   (§3). `_sorting.py`'s two blocks move whole, first line of banner to last line
   of block, with no judgment in them at all. Landing the unambiguous move first
   means that if a gate goes red at the second commit, the `is_logical_path`
   boundary is the only new thing it can be about — the same reasoning PR-19 used
   to put `_index_rows.py` ahead of `_opus.py`.
2. **The dependency runs one way** (§5): associations call transformations,
   never the reverse. Moving the depended-on layer first means that at commit 1
   the callers are all still in core and at commit 2 they are all in the new
   module, so neither commit leaves a half-moved call graph. Either order is in
   fact importable — the calls are `cls.` lookups, not imports — but this order is
   the one a reviewer can check without thinking about the MRO.
3. **Alphabetical base order needs no re-sorting either way.**
   `_AssociationsMixin` sorts before every existing mixin and `_SortingMixin`
   after every existing one, so commit 1 appends its base at the end of the list
   and commit 2 inserts its base at the front; neither commit disturbs what the
   other wrote.

The tree is importable and every gate is green at **both** commits, not just at
the second; that is checked, not assumed.

Neither move commit needs a keep-green content edit inside a moved body (§4 —
no class object is referenced, so PR-19's deferred-import case does not arise
here). Each move commit does carry the header-import edits that the move
requires, itemized in its message: this is the "minimal edits required to keep
the package importable and every active gate green" that §2's PR-discipline
paragraph allows, and it is what PR-17, PR-18 and PR-19 each did.

## 7. Keeping `pdsfile.pdsfile.X` resolving

The measured invariant is `sorted(vars(pdsfile.pdsfile))`: **no name lost**, plus
exactly `_AssociationsMixin` and `_SortingMixin` gained (both underscore names,
so the manifest does not see them).

Counted over the AST at the parent tip, the module-level names the moved bodies
use have these many references left in `pdsfile.py` after the move:

| Name | total refs | inside moved bodies | left in `pdsfile.py` |
|---|---|---|---|
| `os` | 18 | 3 | 15 |
| `_clean_join` | 10 | 4 | 6 |
| `abspath_for_logical_path` | 4 | 1 | 3 |
| `logical_path_from_abspath` | 2 | 1 | 1 |
| **`_needs_glob`** | **1** | **1** | **0 — stranded** |

So `_needs_glob` is the one name this PR strands. It is **private**, so it is not
a frozen manifest member — but it *is* reachable today as
`pdsfile.pdsfile._needs_glob`, and the header's own re-export block exists for
exactly that reason ("carried so that no name reachable as
`pdsfile.pdsfile.<name>` is lost", `pdsfile.py:70–75`, where `_GLOB_CACHE_SIZE`
and `_clean_glob` already sit). Deleting it would break the no-name-lost
invariant every Phase-5 PR has measured; an inline `noqa` and a ratchet grow are
both forbidden. So it moves from the plain `from ._path_utils import (…)` tuple
into that block, in the PEP-484 redundant-alias form:

```python
from ._path_utils import _needs_glob as _needs_glob
```

The other four keep live callers in `pdsfile.py` and so keep their plain import
form; every one of those counts is re-measured at HEAD.

## 10. Ruff ratchet

`per-file-ignores` may only shrink. Same per-code procedure PR-16 through PR-19
recorded, with the two traps their records name (`--isolated` drops
`pyproject.toml`'s `line-length = 100`, and ruff 0.15's default output format no
longer starts a line with the file path):

```
ruff check --no-cache --isolated --output-format concise --select <code> \
           --line-length 100 --target-version py310 <file>
```

1. For every one of the 18 codes in `pdsfile.py`'s entry, run the above against
   the parent's `pdsfile.py`, this branch's `pdsfile.py`, `_sorting.py` and
   `_associations.py`. **Each code must conserve**: parent count = the three
   post-move counts summed.
2. Each new module gets an entry listing **exactly** the codes its moved lines
   trigger, with the same explanatory comment the other moved-module entries
   carry. Every such code must already be in `pdsfile.py`'s entry — the entries
   are a **split**, not a new suppression. **A code that is not already there is
   a §6.4 hard stop.**
3. Any code `pdsfile.py` no longer triggers is **removed** from its entry. This
   is the biggest block yet, so this is the PR where that is most likely; which
   codes leave is recorded either way.
4. The **converse** check, which is easy to skip: run the project's whole select
   set against each new module with **no** per-file entry, and confirm the
   violations reported are exactly the entry.

Moved bodies are **not** restyled to shed an inherited violation — that is a
content edit inside a move, and it belongs to PR-23.

## 12. Hard stops for this PR

Any manifest diff at all; **any** pass/fail set movement, in either direction, in
either mode — this PR is licensed to add no test id; a non-empty mixin/subclass
name intersection (§9); a ruff code needed by either new module that is not
already in `pdsfile.py`'s entry; a moved body that cannot be kept byte-identical
at its extraction commit; a monkeypatch site that cannot be made to fail on wrong
behavior; and any temptation to "tidy" anything inside `associated_parallel`,
which is the deepest method in the file — it reaches the rules, the shelf layer
and the filesystem layer, it recurses, and it is golden-tested by the whole of
`tests/rules/pds3/` and `tests/pds3file/test_pds3file_blackbox.py`.
